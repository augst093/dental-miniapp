# 📋 Технический аудит системы DentaLux (Phase 0)

**Дата аудита:** 4 ноября 2026 г.  
**Проект:** Telegram-бот + Telegram Mini App для стоматологических клиник (B2B SaaS, Ташкент, Узбекистан).  
**Целевой чек:** $450 разово за внедрение + $50/месяц абонентское обслуживание.  
**Цель аудита:** Выявить все архитектурные зазоры, риски потери данных и функциональные пробелы перед запуском коммерческой версии для владельцев клиник.

---

## 1. Архитектура и сетевое взаимодействие

### Текущее состояние
- **Telegram-бот (`dental_ai_bot/`):**
  - Стек: Python 3.11, фреймворк `aiogram 3.x`, клиент `openai` для связи с DeepSeek API.
  - Деплой: Настроен для Railway через Dockerfile (`railway.json`, `Procfile`).
  - Режим работы: Long-polling (`dp.start_polling(bot)`).
  - Обработка событий:
    - Команда `/start` с языковым онбордингом (RU / UZ / EN).
    - Текстовые reply-кнопки меню (быстрый отклик 0 сек).
    - Произвольные вопросы пациентов через DeepSeek API (`deepseek-chat`).
    - Отправка контакта `F.contact`.
    - Приём данных записи из Mini App через `F.web_app_data`.
- **Telegram Mini App (`dental_miniapp/`):**
  - Стек: Next.js 16.4.4 (Turbopack), React 19, Tailwind CSS v4, TypeScript.
  - Деплой: Vercel (`https://dentalminiapp.vercel.app`), готов к деплою на Railway.
  - Режим работы: Клиентское SPA.
- **Механизм связи между Bot и Mini App:**
  - В настоящее время связь **односторонняя**: форма бронирования в `BookingModal.tsx` вызывает `window.Telegram.WebApp.sendData(JSON.stringify(payload))`.
  - Telegram закрывает Mini App и отправляет сообщение с типом `web_app_data` в чат с ботом.
  - Бот перехватывает его через `@dp.message(F.web_app_data)`, сохраняет в SQLite и отправляет алерт в рабочий чат администратора (`ADMIN_CHAT_ID`).

### Выявленные архитектурные зазоры
1. **Отсутствие серверного API в Mini App:** У Mini App нет собственных API-роутов для чтения расписания, проверки занятости слотов и отображения админ-панели.
2. **Однонаправленный поток данных:** Пациент не видит, какие слоты реально заняты, а администратор не может управлять записями прямо из Mini App.
3. **Отсутствие вебхука для продакшна:** Long-polling на Railway уязвим к кратковременным сетевым разрывам.

## 2. Слой данных и персистентность (Data Layer)

### Текущее состояние
- В боте используется SQLite (`data/dental_bot.db`) через `aiosqlite`.
- Таблицы:
  - `users`: `telegram_id`, `username`, `first_name`, `last_name`, `language`, `is_operator_mode`, `created_at`, `updated_at`.
  - `messages`: `id`, `telegram_id`, `role`, `content`, `created_at` (история диалога с LLM).
  - `leads`: `id`, `telegram_id`, `client_name`, `phone`, `service`, `preferred_time`, `summary`, `language`, `status`, `created_at`, `updated_at`.
- В Mini App базы данных нет (все услуги, врачи и цены захардкожены в `src/data/clinicData.ts`).

### Критические риски
1. **Потеря данных при перезапуске на Railway:** В контейнерах Railway файловая система эфемерна. При любом redeploy или кратковременном сбое файл SQLite стирается, если не смонтирован persistent volume.
2. **Отсутствие сущности визита (Appointment) и слотов:** Текущая таблица `leads` хранит просто неструктурированную строку `preferred_time: "Сегодня, 14:00"`. Нет проверки на двойную запись к одному врачу, нет длительности процедуры.
3. **Отсутствие таблицы напоминаний (Reminders):** Напоминания за 24ч и за 2ч в текущей кодовой базе отсутствуют вовсе.

### Решение
- Внедрение **PostgreSQL** (Railway Postgres / Supabase / Neon) как единого источника правды с поддержкой `DATABASE_URL`.
- Использование **Prisma ORM** в Next.js для строгой типизации, миграций и валидации на уровне БД.
- Локальный SQLite-фоллбек для автономной разработки без подключения к сети.
- Единые таблицы: `clinics`, `doctors`, `services`, `patients`, `appointments`, `reminders`, `audit_logs`, `settings`.

## 3. Интеграция с AI-ассистентом (DeepSeek)

### Текущее состояние
- Модель: официальный `deepseek-chat` через OpenAI-совместимый SDK (`AsyncOpenAI(base_url="https://api.deepseek.com")`).
- Параметры: `temperature=0.3`, `max_tokens=250`, таймаут 30 сек, до 3 повторов при ошибках 503/Busy.
- Контекст: `SYSTEM_PROMPT` склеивается с содержимым `dental_ai_bot/data/knowledge_base.json`.
- Инструменты (Function Calling): `register_lead` и `request_human_operator`.

### Выявленные проблемы
1. **Утечка персональных данных пациента в LLM:** В `ai_service.py` (строка 125) имя пациента и username открыто отправлялись в промпт (`user_meta = f"Пациент: Имя: '{tg_name}', Username: '@{username}'"`). Это нарушает требования приватности Phase 7 и Phase 8.
2. **Отсутствие жестких медицинских гардов:** Промпт рекомендует не ставить диагнозы, но не имеет алгоритмического перехвата опасных симптомов (острая нестерпимая боль, сильное кровотечение, запрос конкретных антибиотиков или дозировок обезболивающих).
3. **Дублирование знаний:** Описания врачей, услуг и цен хранятся в двух разных местах — `knowledge_base.json` (в боте) и `clinicData.ts` (в Mini App).

## 5. Безопасность и соответствие закону о персональных данных

1. **Отсутствие валидации `initData`:** Любой пользователь теоретически мог бы вызвать API-маршруты от чужого имени. Необходима криптографическая проверка HMAC SHA-256 с секретным ключом бота (`BOT_TOKEN`) и проверка свежести `auth_date`.
2. **Права администратора:** Должна проверяться принадлежность `user.id` списку `ADMIN_ID` на стороне сервера (server-side authorization).
3. **Согласие на обработку ПДн:** Пациент должен явно подтвердить согласие (`consent_at`) перед первым бронированием.
4. **Право на забвение:** Добавить команду `/delete_my_data` для обезличивания личных данных пациента с сохранением общей статистики.

## 6. Адаптированный план внедрения (Phases 1–9)

| Фаза | Задача | Результат |
|---|---|---|
| **Phase 1** | **Data Model & Appointment Lifecycle** | PostgreSQL-схема через Prisma, статусы визитов (`pending`, `confirmed`, `reschedule_requested`, `cancelled`, `completed`, `no_show`), защита от двойной записи, API слотов. |
| **Phase 2** | **Reminder Engine (Перезапускоустойчивый)** | Таблица `reminders`, воркер с поминутной проверкой, шаблоны напоминаний за 24ч и 2ч с кнопками `Приду / Перенести / Отменить`, алерт админу о неподтвержденных визитах. |

| **Phase 4** | **Owner Report & Weekly Digest** | Экран отчетов за 7/30 дней (доля через бота, no-show rate, спасенные слоты, экономия времени администратора, легкий график) + еженедельный дайджест в Telegram. |
| **Phase 5** | **Demo Mode (`DEMO_MODE=true`)** | Бэйдж «Демо», скрытая панель управления демо («Отправить напоминание сейчас», «Сгенерировать запись на завтра», «Симулировать отмену», сидирование реалистичных данных за 14 дней). |

| **Phase 7** | **AI Assistant Guardrails** | Маскирование личных данных перед отправкой в DeepSeek, отказ от назначения лекарств, мгновенный перевод на экстренную помощь и живого администратора. |
| **Phase 8** | **Security & Privacy** | Валидация `initData` по HMAC-SHA256, чекбокс согласия на обработку ПДн (`consent_at`), команда `/delete_my_data`, валидация номеров `+998`. |
| **Phase 9** | **Polish & Demo Readiness** | Скелетоны загрузки, адаптация под темную тему Telegram, отсутствие горизонтального скролла на 320–360px, проверка 3-минутного демо-сценария. |
